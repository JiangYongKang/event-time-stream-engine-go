# 事件时间流处理引擎（Go，本地可运行）

一个用**本地数据源**（内存 / JSON Lines 文件）与**本地存储**（JSONL 文件 / 内存 sink）
模拟数据接入、事件时间窗口计算与写出的流处理引擎。重点保证：在**乱序、重复、迟到、
故障重启、检查点损坏**等异常链路下，结果**一致、可解释、恰好一次**。

## 快速开始

```bash
# 端到端演示：构造乱序/重复/迟到数据，中途确定性“崩溃”，再从检查点恢复
go run ./cmd/demo

# 全量单测（含竞态检测，强烈建议）
go test -race ./...

# 指定输出目录 / 关闭崩溃模拟
go run ./cmd/demo -out /tmp/stream-demo -crash=false
```

运行 `demo` 会在 `demo-out/` 生成：

| 文件 | 含义 |
| --- | --- |
| `checkpoint/manifest.json` | 最新检查点清单（指向数据文件 + SHA-256 校验和 + 格式版本） |
| `checkpoint/data-<id>.json` | 该检查点的完整状态（窗口、位点、待写出、已确认 ID） |
| `results.jsonl` | 窗口聚合结果（幂等追加，每行一条） |
| `late.jsonl` | 迟到旁路记录（side output，绝不静默丢弃） |
| `events-0.jsonl` | 输入数据源（事件时间由数据自带） |

## 架构与包划分

```
pkg/model       事件 / 窗口 / 结果 / 迟到记录等核心类型
pkg/window      固定滚动窗口分配（窗口归属只由事件时间决定）
pkg/watermark   分区事件时间跟踪、全局水位线（分区取 min）、迟到判定
pkg/state       窗口聚合状态、事件去重集合、已提交窗口边界（并发安全）
pkg/checkpoint  检查点原子持久化、校验和、清单、版本与损坏识别
pkg/source      Source 接口：内存数据源、JSONL 文件数据源（字节偏移位点）
pkg/sink        Sink 接口：内存 sink、JSONL 文件 sink（按 ID 幂等 + fsync）
pkg/engine      编排：并发分区、有界队列背压、检查点屏障、定稿与恢复
cmd/demo        本地端到端演示（含确定性故障注入）
```

## 时间与水位语义

- **事件时间（event time）**：由事件自带字段 `event_time` 决定，与到达/处理时刻无关。
- **窗口归属**：固定滚动窗口 `[Start, End)`，以 Unix 零时刻对齐。同一事件时间无论何时到达、
  到达几次，都映射到**同一个确定性窗口 ID**（`key@startNS/endNS`）。乱序到达不改变窗口归属。
- **水位线（watermark）**：
  `watermark = min(各分区观察到的最大事件时间) - outOfOrderness`，且**单调不减**。
  分区需先注册；尚未产生事件的慢分区会压住全局水位（标准流处理语义），避免提前关闭窗口。
  晚于水位线到达但仍在允许范围内的事件属于“乱序但接受”，**不会**让水位后退。
- **允许迟到（allowed lateness）**：窗口在
  `windowEnd + allowedLateness <= watermark` 时才**定稿（finalize）**。在此之前，
  属于该窗口的迟到/乱序事件仍会更新其累计值。
- **迟到判定**：当 `eventTime + allowedLateness < watermark` 时，事件不再进入窗口：
  - 进入**迟到旁路** `late.jsonl`，记录原因（`EXCEEDS_ALLOWED_LATENESS`
    或 `WINDOW_ALREADY_COMMITTED`）、当时水位线与允许迟到时长；
  - **绝不静默丢弃**，也**绝不回改已经提交的窗口结果**。
- **去重优先于迟到判定**：同一事件 ID 无论以多乱/多晚的形式重复到达，都不会被重复计入，
  也不会被当成“新的迟到数据”旁路。
- **输入结束**：所有分区读到源末尾后，水位线推进到一个可序列化的“无穷大”时间，
  用于定稿所有剩余窗口（正常排空，不是故障路径）。

## 一致性保证的范围

引擎在“**本地、单实例、单写者目录**”范围内提供恰好一次（exactly-once）结果语义：

1. **提交顺序（先持久化、后写出）**。每次提交在检查点屏障内：
   1. 原子写入检查点（覆盖窗口状态、各分区读取位点、已定稿待写出结果、迟到待写出、已确认 ID）；
   2. 检查点落盘成功后，才把结果/迟到记录幂等写入 sink；
   3. sink 确认成功后才把这些项从“待写出”集合移除。
2. **崩溃恢复的两种情况都安全**：
   - 崩溃发生在检查点**之前**（批次只在内存）：恢复后从旧位点**整批重放**；
     事件去重集合 + sink 幂等 ID 保证不会重复计入/重复写出。
   - 崩溃发生在检查点**之后、sink 写出之前/之中**：结果仍记录在检查点的
     `pending_results`，恢复时先按 ID 幂等补写；已写出的不会重复，未写出的不会丢。
3. **确定性结果 ID**：结果 ID 即窗口 ID（`key@start/end`），sink 按该 ID 去重，
   重放不会产生重复物理行。
4. **位点语义**：内存源为“下一条事件下标”，文件源为“下一行字节偏移”；
   位点只在整批处理成功后在内存推进，并随下一个检查点持久化。
5. **并发安全**：多分区 worker 对 `store + 水位线` 的“判定 + 更新”由单一状态锁串行化，
   检查点在屏障下获得一致快照（无半更新、无窗口错位）。`go test -race` 全程干净。

**不在保证范围内**（本地模拟的边界）：多实例/分布式协调、跨机器 sink 的事务、
对外部非幂等系统的两阶段提交、检查点目录被多个进程同时写入。

## 检查点格式与失效识别

目录布局：

```
checkpoint/
  manifest.json      # 最新清单（原子 rename 替换）
  data-<id>.json     # 状态数据（先落盘，再被清单引用）
```

写入顺序是“先数据、后清单（原子替换）”，因此崩溃只会留下可识别的中间产物。
恢复时对失败原因做**可区分**的判定，绝不从中间状态静默继续：

| 错误哨兵 | 触发条件 |
| --- | --- |
| `ErrNoCheckpoint` | 目录为空，全新启动 |
| `ErrCorruptManifest` | 清单缺失/无法解析/字段不全 |
| `ErrCorruptData` | 数据文件 SHA-256 与清单不符或无法解析 |
| `ErrInconsistent` | 清单指向的数据文件丢失，或清单/数据 ID 不一致 |
| `ErrDanglingCheckpoint` | 只有数据文件、没有有效清单（写入中途崩溃的悬空文件） |
| `ErrUnsupportedVersion` | `format_version` 与当前版本不符（旧的/不兼容检查点） |

引擎遇到上述任何损坏都会**拒绝启动**并返回带哨兵的错误。

## 背压与资源上限

- 每个分区是 `feeder -> 有界批次队列 -> worker` 流水线。
- 队列容量 `PendingQueueCap` × `BatchSize` 即该分区**待处理数据的内存上界**，
  消费不过来时 feeder 在入队处**阻塞/限速**，数据不会无界堆积。
- 触发上限时：累计 `Metrics.BackPressure` 计数并打印
  `[backpressure] ... queue full ... blocking feeder` 日志，可观测。
- 可用 `Config.ProcessDelay` 注入单事件处理耗时，人为制造慢处理以验证背压。

## 可观测性

运行日志（单测中也会打印）覆盖：

- `[event]` 每条事件：ID、键、事件时间、分区、值、**判定到的窗口**；
- `[dup]` 重复事件及其被忽略；
- `[late]` 迟到事件、水位线、允许迟到时长与旁路原因；
- `[window]` 窗口定稿区间、count/sum 与当时水位；
- `[checkpoint]` 检查点 ID、活动窗口数、各位点、待写出数量、水位；
- `[recover]` 恢复依据的检查点 ID、水位、位点、活动/已提交窗口、待写出重放；
- `[backpressure]` 队列触顶阻塞；`[crash]`/`[stop]` 故障注入/干净停机。

指标见 `engine.SnapshotMetrics()`：处理数、重复丢弃、迟到旁路、已提交窗口、
检查点数、背压次数、恢复来源检查点、当前水位。

```

pkg/state       聚合、去重、允许迟到期内不关闭、定稿后拒绝回改、快照恢复

pkg/sink        内存/文件 sink 幂等；重开重建索引、物理行不重复
pkg/engine      乱序归属、重复、迟到旁路、崩溃重放恰好一次、
                从“含活动窗口的中途检查点”恢复续跑、多分区并发、背压可观测、
                损坏检查点拒绝启动、一次跑完 vs 崩溃重放结果确定性一致
```
